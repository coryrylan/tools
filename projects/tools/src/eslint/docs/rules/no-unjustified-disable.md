# tools/no-unjustified-disable

Require every `eslint-disable*` directive comment to explain, in the diff, why it exists.

## Why this matters for agents

An agent under pressure to turn CI green will reach for `eslint-disable` before it reaches for a real fix. Once the comment is silent about _why_, a reviewer - human or another agent - can't tell a legitimate, reviewed suppression from one hiding a bug, and a blanket `eslint-disable` silences rules nobody has actually looked at, including ones added after the comment was written. Requiring a `-- <reason>` (and, by default, an explicit rule list) turns every suppression into something greppable and reviewable instead of a black box.

## Examples

❌ Incorrect:

```js
// eslint-disable-next-line no-console
console.log(value);

/* eslint-disable */
doRiskyThing();
```

✅ Correct:

```js
// eslint-disable-next-line no-console -- CLI tool; stdout is the product, not debug noise
console.log(value);

/* eslint-disable no-console, no-unused-vars -- generated bindings, see scripts/codegen.js */
doRiskyThing();
```

## Options

```ts
interface Options {
  /**
   * When true (the default), the directive must also name at least one
   * specific rule - a blanket `eslint-disable`/`eslint-enable` with no rule
   * list is rejected even if it carries a justification.
   */
  requireRuleIds?: boolean; // default: true
}
```

## When not to use it

Skip this rule in codebases that intentionally rely on blanket, undocumented `eslint-disable` comments (e.g. large-scale automated migrations where every suppression sharing one boilerplate comment is an accepted trade-off), or where directive comments are generated by tooling that doesn't support attaching a description.
